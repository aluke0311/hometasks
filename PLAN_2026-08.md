# Home Tasks — Hardening + Delight Plan (August 2026)

Written 2026-08-03 by reading this repo against the **wardrobe app** (`~/Documents/Claude Code/wardrobe_app`),
a sibling personal app that has been through ~14 months of daily use, several
product re-interviews, and a lot of expensive mistakes. Everything in Part 1 is a
lesson that app paid for; everything in Part 2 is a feature that app found people
actually open every day.

**How to use this document.** Work top to bottom. Each item is self-contained:
what, why, where, spec, how to verify, export status. Follow the existing
`app-update` skill for the mechanics (verify in preview → bump `APP_VERSION` →
commit + push → state export status). One commit per numbered item.

**Line numbers are as of 2026-08-03 and will shift.** Anchor on function names,
re-grep before editing — the standing rule in the skill.

**Ground truth about what was verified.** Every claim in Part 1 was checked by
reading the code in this repo on 2026-08-03. Where something is a hypothesis that
needs her real `localStorage` data to confirm, it says so explicitly (only F-4 and
Fix 7 are in that category).

---

## Context: the five lessons behind this plan

The wardrobe app learned these the hard way. They're worth stating because they
explain *why* the fixes below are ordered the way they are.

1. **Live personal data is irreplaceable, and the app is the only thing standing
   between it and zero.** Wardrobe has Supabase behind it and still treats data
   safety as the top constraint. Home Tasks has `localStorage` and nothing else.
2. **A rule you have to remember is a bug you will eventually ship.** Wardrobe's
   docs were full of "don't forget to also update X" warnings. Every one of them
   was eventually forgotten. The fix is always structural, never a better warning.
3. **A test that has never failed is not a test.** Wardrobe's self-test suite sat
   at "green" for a month while silently scoring *cached, stale* code. Two other
   cases passed vacuously against 404s. When you add a case, mutate the thing it
   guards and watch it go red **in the same session**.
4. **Derive, don't store.** Every stored aggregate eventually disagrees with the
   events it was derived from, and once it does it can never be repaired.
5. **A wrong guess costs more trust than hand-entry costs taps.** Wardrobe built a
   layer that inferred things about the user, patched it four times in one day, and
   then deleted it entirely. Offers she accepts are fine. Decisions made for her
   are not.

# PART 1 — Fixes

## Fix 1 — Flush pending saves on `pagehide` (P0, data loss)

**What's wrong.** `saveState()` debounces writes by 300 ms. There is **no
`pagehide`, `visibilitychange`, or `beforeunload` handler anywhere in the file** —
I grepped for all three. If the app is backgrounded or closed within 300 ms of a
mutation, that mutation is lost.

`completeTask` correctly calls `saveNow()` (the synchronous path), so the main
daily action is safe. But roughly 45 other mutation sites call the debounced
`saveState()`, including several that write real, non-reconstructable data:

- `markTaskDue` (`index.html:1433`) — writes `state.completions[id]`
- `flagTask` (`:1428`), pin, snooze, remove
- every preset generate/load (`:2443`, `:2460`, `:2515`, `:2542` … `:2695`)
- budget edits, zone changes, seasonal month edits

**Why it matters here more than in wardrobe.** Wardrobe posts to Supabase, so a
dropped local write costs a session. Here `localStorage` *is* the database. The
realistic scenario is not exotic: tap the last thing, put the phone down, iOS
suspends the tab. iOS is aggressive about this.

**Where.** `saveState` / `saveNow`, `index.html:822–843`. Register the handler in
`init()` (`:4107`).

**Spec.**

```javascript
let saveDebounceTimer = null;

function saveNow() {
  if (saveDebounceTimer) { clearTimeout(saveDebounceTimer); saveDebounceTimer = null; }
  try {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(state));
  } catch (e) {
    console.error('Storage save error:', e);
  }
}

function saveState() {
  if (saveDebounceTimer) clearTimeout(saveDebounceTimer);
  saveDebounceTimer = setTimeout(saveNow, 300);
}
```

Then in `init()`:

```javascript
// A backgrounded tab may never run another line of JS. Flush before it goes.
window.addEventListener('pagehide', saveNow);
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') saveNow();
});
```

**Two things this deliberately changes.**

- `saveState` is no longer `async` and no longer uses the `isSaving` guard. That
  guard sat at the top of the debounce callback as `if (isSaving) return;` — it
  returned *without rescheduling*, i.e. a silent dropped write. Because
  `localStorage.setItem` is synchronous, `isSaving` is practically never true when
  the callback runs, so this is a latent branch rather than a live bug. It should
  still go: it is a "silently do nothing" path on the save route, and there is no
  reason for one.
- `saveNow` now cancels any pending debounce. Previously a `saveNow()` could be
  followed 200 ms later by a debounced write of *the same* `state` object —
  harmless today because they share one object reference, but it means the two
  functions aren't actually coherent with each other.

`loadState`/`saveState` being `async` appears to be vestigial (there is no remote
persistence anywhere in the file). Leave `loadState`'s signature alone —
`init()` awaits it — but `saveState` has no awaited callers.

**Verify.** In the preview console: `state.zone = 3; saveState();` then
immediately `window.dispatchEvent(new Event('pagehide'));` then
`JSON.parse(localStorage.getItem('hometasks_v8')).zone` → `3`. Before the fix the
same sequence within 300 ms reads the old value.

**Export status.** ✅ No export needed.

## Fix 2 — Make `loadState` spread-based so new fields can't be dropped (P0, structural)

**What's wrong.** `loadState` (`index.html:781–812`) rebuilds state field by field
from an explicit whitelist. Any field not named there is silently discarded on
load. `applyImport` (`:3670–3690`) has the identical shape and the identical
problem.

This is *why* CLAUDE.md and the `app-update` skill both carry the warning "adding
state requires a default in all three of `defaultState()`, `loadState()`, and
`applyImport`, or import silently drops the field." That warning is doing real work
right now — which is exactly the smell. Lesson 2: a rule you have to remember is a
bug you will eventually ship. This one has been shipped at least once already
(`applyImport` field gaps, fixed 2026-06-15).

**Where.** `loadState` `:760`, `applyImport` `:3670`.

**Spec.** Replace the explicit object literal in `loadState`'s `if (raw)` branch
with a spread over `defaultState()`, keeping only the fields that need genuine
transformation:

```javascript
const parsed = JSON.parse(raw);

// Backfill: a base task added since the user's last visit has no completion
// timestamp; without this daysOverdue() would read ~20,000 days overdue.
const completions = parsed.completions || {};
const _now = Date.now();
TASKS.forEach(t => { if (completions[t.id] == null) completions[t.id] = _now - t.freq * 86400000; });

return {
  ...defaultState(),
  ...parsed,
  // fields needing real migration logic, applied after the spread:
  completions,
  budgetWeekday: parsed.budgetWeekday != null ? parsed.budgetWeekday : 45,
  budgetWeekend: parsed.budgetWeekend != null ? parsed.budgetWeekend : 90,
  mode: (parsed.mode === 'survival' ? 'maintenance' : parsed.mode) || 'maintenance',
  paused: !!parsed.paused,
  seasonalDefaultsApplied: !!parsed.seasonalDefaultsApplied,
};
```

Apply the same shape to `applyImport`.

**What this buys.** The three-place rule collapses to one place (`defaultState()`).
A new field added to `defaultState()` is automatically defaulted on load *and* on
import, forever. Update CLAUDE.md's "Editing pitfalls" section and the
`app-update` skill's watch-out list to say so — the warning becomes obsolete and
should be deleted, not kept "just in case."

**One caveat to check while implementing.** `...parsed` now carries through fields
that `defaultState()` doesn't know about — including transient ones like
`_dealPreferTier`, which is supposed to be deleted immediately after use. That's
fine (it's deleted on the next deal), but confirm nothing depends on unknown fields
being *stripped* on load. I read the load path and found nothing that does, but
this is the one behavioural difference worth a deliberate look.

**Verify.** In preview: add a junk field, save, reload, confirm it survives *and*
that a field present in `defaultState()` but absent from stored JSON gets its
default. Then round-trip an export → import and confirm the same.

**Export status.** ✅ No export needed. (Take a manual backup first anyway — this
touches the load path, and Lesson 1.)

## Fix 3 — A self-test harness, run as a deploy gate (P0, leverage)

**What's wrong.** There are no tests. The app's core is a pile of pure functions
with subtle, documented-as-critical invariants, and every one of them is currently
protected only by care.

**Why this is the highest-leverage item in the document.** Wardrobe's
`migration/selftest.html` grew to 231 cases and became a required gate for any
logic change. It repeatedly caught real regressions that reading the diff did not.
Home Tasks' logic is, if anything, *more* testable — no network, no auth, no
photos, pure functions over a plain state object.

**Where.** New file `selftest.html` at repo root (or `test/selftest.html`). It must
not be loaded by `index.html` — it's a separate page you open.

**Spec.**

Same architecture as wardrobe's, which is worth copying because its failure modes
are already known:

- The harness page loads `index.html` in an `<iframe>` and asserts against the
  functions inside it.
- App globals are top-level `const`/`let` inside one `<script>`, so they are **not**
  visible on `iframe.contentWindow`. Wardrobe solves this by injecting a tiny
  eval-bridge into the frame:
  ```javascript
  // appended inside the iframe document
  window.__get = (expr) => eval(expr);
  ```
  then `const W = frame.contentWindow; const scoreTask = W.__get('scoreTask');`
- **Cache-busting is the part that goes wrong.** Wardrobe's harness silently tested
  stale cached code for a month. Home Tasks is a single file, which makes this much
  easier: fetch `index.html` with `cache: 'no-store'`, **throw if `!res.ok`** (a
  404 must never be silent), and hand the text to the iframe via `srcdoc`. Add one
  case asserting that a live function's `.toString()` appears in the freshly
  fetched text — if the iframe is stale, that case goes red.
- Since the tests must run against a *controlled* state, expose a way to swap
  `state`: either `W.__get('state')` mutation, or better, have each case build its
  own fixture object and call functions that take state explicitly where possible.
  Where they don't (most of them read the `state` global), save the real state,
  overwrite, run, restore in a `finally`.

**The starting case list** — these are the invariants the docs already call
critical, plus the bug classes that have actually bitten:

*Preset integrity (highest value — this bug class has already shipped once)*
1. Every id in every preset constant (`FULL_RESET_TASKS`, `GOING_OUT_TASKS`,
   `EXPRESS_RESET_SECTIONS`, `WEEKLY_RESET_SECTIONS`, `RETURN_HOME_SECTIONS`,
   `BEFORE_CLEANERS_SECTIONS`, `RECOVERY_SECTIONS`, `POST_ILLNESS_SECTIONS`,
   `EVENING_SHUTDOWN_FIXED`, `EVENING_TIDY_POOL`, `ROOM_PRESETS`) resolves in
   `TASKS`. **I ran this check on 2026-08-03: currently clean, 180 task ids, zero
   dead references.** That's the point — it costs ~20 lines and permanently retires
   the class. This supersedes the ad-hoc Python scan in the `app-update` skill;
   once it's a case, delete the scan from the skill so there's one gate, not two.
2. Every `ROOM_PRESETS` room id maps to a real room used in `TASKS`.

*Scoring*
3. `scoreTaskParts` components sum to `scoreTask` for a `freq <= 60` task (the
   jitter only applies above 60, so they must agree exactly below it). These are
   documented as "implement one in terms of the other so they can never drift" —
   pin it.
4. Starvation reduction is capped at `freq * 0.15`: a task with starvation 999 and
   `freq` 7 gets no more than `-1.05`. **This is the cap CLAUDE.md calls critical.**
5. Overdue penalty is capped at `freq * 0.8`.
6. Overdue weight is 0.5 in `maintenance` and 0.8 in `catchup`.
7. A flagged task scores at least 50 lower than the same task unflagged.
8. Zone bonus applies only to tasks in the effective zone, and zone-less rooms
   (`Whole House`, `Robot`, `Downstairs`, `Upstairs`) never receive it.

*Dealing*
9. `dealHand` never exceeds the budget except for the always-assigned tasks
   (`c_fountain`, one laundry load) and the first flagged task.
10. At most one laundry "load" task per hand.
11. Laundry "process" steps (`l_start`, `l_dryer`, `l_fold`, `l_put_away`) are
    suppressed when no load is assigned, pinned, or completed today.
12. `byfreq` mode sorts by raw frequency, and flagged tasks still fill first (the
    documented reason flagged handling is special-cased in that mode).
13. Heavy tasks (>15 min) are capped at 2 per hand.
14. `inProgress` tasks are carried into a newly dealt hand.
15. Out-of-season tasks (`taskMonths`) are excluded from the pool and accrue no
    starvation.

*State / time*
16. `taskTime` returns `task.time` under 3 samples and the median at 3+ (check both
    odd and even sample counts).
17. Vacation resume shifts `completions` forward by the pause duration and leaves
    `completionHistory` untouched.
18. `loadState` backfills a `TASKS` entry missing from `completions` to `now − freq
    days`, i.e. exactly due, not 20,000 days overdue.
19. Round-trip: `defaultState()` → export JSON → `applyImport` → deep-equal. This
    is the case that makes Fix 2 permanent.
20. `completeTask` on an unknown id is a no-op and does not corrupt state.

*Version hygiene*
21. `APP_VERSION` matches the format CLAUDE.md documents (`YYYY-MM-DD vN`). See
    Fix 6 — it currently doesn't match what the skill says.

**Non-negotiable process rule.** For each case: write it, run it, then **break the
thing it guards and watch it go red**, then restore. In the same session. Wardrobe
shipped two cases that passed vacuously and one that drove a re-render with no data
behind it; all three reported success for weeks. Note in the commit body that each
new case was mutation-checked.

**Then make it a gate.** Add to the `app-update` skill, Mode A step 4: any change
to scoring, dealing, state shape, or presets requires `selftest.html` green before
commit. Pure CSS/copy/task-text changes are exempt.

**Verify.** The suite verifies itself; the summary line reads `N/N passed`.

**Export status.** ✅ No export needed (new file, `index.html` untouched — no
`APP_VERSION` bump required for this one).

## Fix 4 — Derive `yearStats` instead of accumulating it (P1, correctness)

**What's wrong.** `bumpYearStats` (`index.html:1312`) maintains a stored running
total:

```javascript
ys.minutes = Math.max(0, ys.minutes + taskTime(task) * delta);
```

`taskTime()` returns the *learned median* of recorded actuals, which changes as
samples accumulate. So a year's `minutes` total is a blend of estimates taken at
different moments, in an order that no longer exists anywhere. It cannot be
recomputed, cannot be corrected, and will drift further from truth every time an
estimate improves. Same for `count`, `byTask`, `byRoom`, `byMonth` — all derivable
from `completionHistory`, all stored anyway.

This is Lesson 4, and it's the exact mistake wardrobe made and then wrote a
"zero new columns" rule to prevent.

**Why it exists.** Almost certainly because `completionHistory` is capped at 100
entries per task (`:1345`, `:1413`). A daily task loses its history after ~100
days, so a year total genuinely can't be derived from it. **The cap is the actual
bug; the accumulator is a symptom.**

**Where.** `bumpYearStats` `:1312`, history caps `:1345` and `:1413`, the year
render `:3299–3308`, state field in `defaultState` `:757` / `loadState` `:812` /
`applyImport` `:3690`.

**Spec.**

1. **Raise the history cap.** 180 tasks × 800 timestamps ≈ 1.4 MB of JSON worst
   case, against a ~5 MB `localStorage` budget, and only daily tasks would ever
   approach it. Set the cap to **1000** (≈ 2.7 years of daily), or drop it entirely
   and prune anything older than 3 years instead — the second is better, because it
   bounds by time rather than by count and so treats a daily and a twice-yearly task
   consistently. Prefer time-based pruning.
2. **Write `deriveYearStats(year)`** — one pass over `completionHistory` producing
   `{count, minutes, byTask, byRoom, byMonth, since}`. `minutes` uses the *current*
   `taskTime()` for every completion, so the number is internally consistent and
   improves as estimates improve.
3. **Keep the stored `yearStats` for years that predate the change**, since their
   history is already truncated. Render derived values for any year whose earliest
   `completionHistory` entry precedes that year's start; fall back to the stored
   bucket otherwise. Label the fallback honestly ("counting since …", which the
   current code already does at `:3302`).
4. **Delete `bumpYearStats` calls** from `completeTask`/undo/backdate once (2) and
   (3) are live. Leave the `yearStats` field in state — it's read-only history now.

**Also fix while in there.** `bumpYearStats` sets `since: todayStr()` even when
`ts` is a backdated timestamp, so backdating a completion into a fresh year records
the wrong start date. Moot once derived, but note it in the commit.

**Verify.** Case in the self-test: build a `completionHistory` fixture spanning two
years, assert `deriveYearStats` counts, minutes, and per-room totals; assert that
changing `actualTimes` changes the derived minutes (the whole point) while the
stored accumulator would not have.

**Export status.** ✅ No export needed — nothing is removed from stored state.
**Recommend a manual backup first regardless**, since this touches how history is
pruned.

## Fix 5 — One number, one function (`t.time` vs `taskTime()`) (P1, trust)

**What's wrong.** CLAUDE.md files this under "minor known behaviors": *Stats "est.
effort" uses static `time` while Budget Insight uses learned `taskTime()`.* It's
worth promoting from "minor" — wardrobe's experience is that this class of drift is
precisely what makes a user stop believing the numbers, and it's the cheapest fix
in the file.

Raw `t.time` survives at:

- `index.html:2732` — preset checklist time total
- `:2752` — preset card time display
- `:3050`, `:3051` — `ROOM_PRESETS` quick/deep time totals
- `:3414` — Settings "daily minutes" summary

Everything else (hand, sprint, copy-to-clipboard, budget filling, Stats effort at
`:3093`) uses `taskTime()`. So a preset says one number and the sprint you launch
from it says another, for the same tasks.

Wardrobe hit the identical shape as "a wear is a DAY, never a row" — the same fact
computed two ways across six surfaces — and fixed it with one helper everything
routes through.

**Spec.** Replace every raw `t.time` sum in a *display or budget* context with
`taskTime(t)`. `t.time` remains correct in exactly two places: the task editor
field (`:3876`, it edits the static estimate) and the "est 10m" half of the learned
hint (`:3795`, which is explicitly comparing the two).

Consider a comment above `taskTime` naming it the single source for "how long will
this take", so the next edit doesn't reintroduce the split.

**Verify.** Self-test case: seed `actualTimes` for a task with 3+ samples whose
median differs from `time`, then assert the room-preset total, the sprint total,
and the Stats effort for the same id all agree.

**Export status.** ✅ No export needed.

## Fix 6 — Update visibility: version check + what's new (P2, quality of life)

**What's wrong.** GitHub Pages caches hard. Right now, noticing you're on a stale
build requires *suspecting* it, opening Settings, and comparing `APP_VERSION` by
eye against… nothing, really. There's a Reload card, but you have to already
believe something is wrong.

Wardrobe solves this with `checkForNewVersion()`: on load, `fetch` its own deployed
page (Range request for the first 2 KB), read a `<meta name="app-version">`, compare
to the constant, and toast "Update available" with a reload action. Reload must be
`location.replace(url + '?v=' + Date.now())` — a plain `location.reload()` can
re-serve the same cached copy.

It also has `WHATS_NEW`: a short changelog string bumped alongside `APP_VERSION`,
toasted once on the first run of a new version (`store` key `seenVersion`). That
matters more here than there, because **Bob uses this app and never sees the
commits.**

**Spec.**

1. Add `<meta name="app-version" content="…">` to `<head>`, matching `APP_VERSION`.
2. `checkForNewVersion()` on load: `fetch(location.href, {cache:'no-store'})`, parse
   the meta out of the first few KB, compare, toast with a Reload chip on mismatch.
   Fail silently on any network error — this must never block boot.
3. `const WHATS_NEW = '…'` next to `APP_VERSION`. On boot, if
   `state.seenVersion !== APP_VERSION`, toast it and store the new version.
   (`seenVersion` is new state → `defaultState()` only, once Fix 2 has landed.)
4. **Add both to the `app-update` skill's Mode A**, so the version, the meta tag,
   and `WHATS_NEW` are bumped together. Wardrobe keeps three things in lockstep and
   the self-test pins all three; here it's two plus a changelog, and self-test
   case 21 should pin the meta ↔ constant agreement.

**While you're here — a small documentation drift.** `APP_VERSION` is currently
`'2026-07-09 v1'`. CLAUDE.md documents the format as `YYYY-MM-DD vN` (commit
`0373204` made that switch), but the `app-update` skill still says
`const APP_VERSION = 'YYYY-MM-DD';`. Fix the skill to match reality.

**Verify.** Temporarily edit the deployed meta (or stub the fetch in preview) and
confirm the toast fires and the reload lands on the new build.

**Export status.** ✅ No export needed (`seenVersion` defaults cleanly).

## Fix 7 — Starvation: consider a reserved slot, not a bigger bonus (P2, needs data first)

**Hypothesis, not a verified defect.** Flagging it because the wardrobe analogue was
load-bearing and non-obvious.

Wardrobe's suggestion pool (the "rack") reserves a hard **20% of every slot** for
deliberately-cold items. The reason is structural: without it the pool calcifies —
worn → in pool → suggested → worn — and over years it silently shrinks the working
wardrobe, i.e. *the mirror causes the thing it measures*. The key insight is that a
**score bonus only means "hope it wins"; a quota guarantees it appears.**

Home Tasks relies on a bonus: the starvation counter, capped at `freq * 0.15`. The
cap is correct and necessary (CLAUDE.md is right that removing it lets long-interval
tasks dominate). But combined with the heavy-task cap of 2 per hand, the
`removedToday` exclusion, and a budget of 45 minutes on weekdays, there may be a
class of task — long `freq`, high `time` — that can essentially never win a slot and
just accrues starvation forever.

**Before building anything, measure.** In the browser console on her real data:

```javascript
Object.entries(state.starvation)
  .sort((a,b) => b[1]-a[1]).slice(0,25)
  .map(([id,n]) => { const t = getAllTasks().find(x=>x.id===id);
    return [id, n, t && t.freq, t && t.time, t && t.room]; })
```

If there's a long tail of tasks with high starvation counts and high `time`, the
hypothesis holds. If starvation counts are all small, it doesn't — the system is
working and this item should be closed as "checked, not a problem."

**If it holds, the fix is a quota, not a bigger bonus.** Reserve one slot per hand
(or one per week) for the single most-starved Tier B/C task, dealt outside the
budget the way `c_fountain` and the laundry load already are. That's a small,
well-precedented change to `dealHand` — the always-assigned mechanism exists.

**Export status.** ✅ No export needed.

## Fix 8 — Look at the screens (P1, process not code)

Wardrobe's single most embarrassing bug: the primary "Log today's wear" button
rendered as a **181 px stub in a 390 px column for months**. A `<button>` sizes to
its content regardless of `display:block`; it needed an explicit `width`. Invisible
to code review, obvious within five seconds of looking at the app. Three separate
trip-planner defects were later found the same way — by rendering the screen and
reading it, not by tests.

Home Tasks has the setup for the same bug: `.add-btn` (`index.html` CSS, line ~149)
defines no width and is used with ad-hoc inline `style="width:100%"` at call sites
(e.g. `:3528`). I did **not** find a live instance — but a class whose full-width
behaviour depends on every call site remembering an inline style is one edit away
from one.

**Do this once, deliberately:** open the preview at 390 px wide, walk all six tabs
in light *and* dark mode, and look at every screen. Note anything that's the wrong
width, clipped, misaligned, or unreadable. Fix them in one commit. Then consider
giving `.add-btn` a `width: 100%` variant class so the intent lives in CSS.

**Export status.** ✅ No export needed.

# PART 2 — New features

Ranked by (delight × cheapness). The organizing principle comes from wardrobe's
2026-07 product re-interview, which produced two findings that apply directly here:

> **The stats ARE the daily reward.** She opens the stats page *daily*, to look
> rather than to learn. Offered twelve analytical features to cut, she kept eleven.
>
> **The app is over-*presented*, not overbuilt. Compress, don't delete.** Given one
> round of work she chose a coherence pass over new features.

Home Tasks is in the same position: six tabs, ~20 presets, 180 tasks, and a Stats
tab that has quietly become the most interesting screen. Most of what follows is
*reframing what's already computed* rather than computing new things.

---

## F-1. "Things you might be wrong about" — reframe Completion Cadence ⭐ build first

**The idea.** Wardrobe's most-loved feature is a page where **the app disagrees with
what she told it**: pieces she tagged one way that the wear history says are
something else. The disagreement is more interesting than either number alone.

**Home Tasks already computes this.** `cadenceInfo()` (`:3176`) compares median real
interval to the target `freq` and colour-codes the gap, including the blue "you do
this *more* often than you said" case. `setTaskFreq` (`:3185`) is the one-tap
adoption. It's all there — sitting as the last card on the Stats tab, described in a
paragraph of explanatory text.

**So this is a presentation change, not a feature build.** Give it a name and a
top position:

- Title it something with a point of view — **"What you actually do"** — and lead
  with the count: *"11 tasks run on a different schedule than you set."*
- Two sections, because they're genuinely different feelings:
  - **Behind** (red/amber): "You said every 7 days. You really do it every 19."
    → *Change target to 19d* (already built) or *leave it, it's aspirational*.
  - **Ahead** (blue): "You said every 30 days. You really do it every 11." → this
    is the delightful half and it's currently buried. It means either the target is
    too lax, or she's over-cleaning something and could *get time back*.
- Keep the existing tap-to-edit and +Today affordances.

**Why it works.** It's the only screen that tells her something she didn't know,
sourced entirely from her own behaviour, with a one-tap way to act. That's the
whole wardrobe thesis in one card.

**Cost.** Small — reorganising an existing render function.

## F-2. Year in Pixels + Year in Review ⭐ (depends on Fix 4)

**The idea.** Wardrobe has two related things people open for pleasure:

- **Year in Pixels** — a 53×7 grid, one cell per day of the year, shaded by
  intensity. Immediate, wordless, and honest about the gaps.
- **Year in Review** — a card stack: totals, the champion, the dead weight, the
  longest streak.

**Home Tasks is most of the way there.** There's a 13-week heatmap and the new
This-Year counters. The upgrades:

1. **Extend the heatmap to a full year**, shaded by minutes (or task count) per day.
   Wardrobe's hard-won detail: use **fixed-width cells (11 px) with horizontal
   scroll**, never `1fr` columns — `1fr` is circular against the cells' own width and
   the grid collapses.
2. **Year in Review card stack**, derived (Fix 4) rather than accumulated:
   - total tasks, total hours
   - the room that got the most attention, and the one that got the least
   - the task done most times (with the count)
   - the task you snoozed most — funny, and true
   - longest streak, and whether this year beat last year
   - month-by-month bar, which is `byMonth` you already have
3. **Room heat.** Room Pressure (`:3316`) already ranks rooms by how overdue they
   are. Add the flip side — *attention received this year per room* — so the two
   read as a pair: what's neglected vs. what's loved.

**Why Fix 4 first.** Every one of these is a slice of `completionHistory`. Once
`deriveYearStats` exists they're all cheap; without it they're new accumulators,
each one a fresh instance of Lesson 4.

**Cost.** Medium, and most of it is layout.

## F-3. Milestones — one per completion, each once ever ⭐

**The idea.** Wardrobe fires at most **one** milestone per logged wear, and each
milestone key can fire **once ever** (a seen-set in storage). The cap was designed
in from the start, and that discipline is why it stayed charming instead of becoming
noise.

**Rungs that fit a house**, in priority order (first match wins):

- **First ever** — "First time you've done this since the app started."
- **Rescued** — a task not done in 180+ days finally gets done. Very satisfying.
- **Round numbers** — 10th / 25th / 50th / 100th time.
- **Room sweep** — *every* task in a room done at least once this season. This is
  the direct analogue of wardrobe's "every pair of shoes worn this year," which was
  its best-received milestone, and it maps beautifully onto zone cleaning.
- **Streak record** — beats the stored best (min 5 days).

**Implementation notes.**
- New state: `milestones` (seen-set of keys) and `bestStreak`. With Fix 2 landed
  that's a one-line addition to `defaultState()`.
- Compute in `completeTask` **after** the completion is recorded; return at most one.
- **Don't let it collide with the Undo toast.** Wardrobe's rule: a milestone toast
  replaces the plain "Logged ✓" confirmation but **never** the Undo affordance.
  Queue it behind any open modal.
- Undo must un-spend the milestone key, or a mis-tap permanently burns "first ever."

**Cost.** Small–medium. Very high delight per line.

## F-4. "On this day" (needs the history cap raised — Fix 4)

**The idea.** Wardrobe surfaces a small row on the home screen: *what you wore on
this date in a previous year*. Pure delight, no action, ~30 lines.

**Here:** *"A year ago today: gutters, back porch swept, sheets."* Or, better for a
house, the seasonal version — *"Last August you did the window screens. Due again
in 3 weeks."*

**This is currently impossible** because `completionHistory` is capped at 100
entries per task, so a year-old completion of anything frequent is already gone.
Raising the cap (Fix 4, step 1) is what unlocks it — which is a nice illustration
that the boring fix and the fun feature are the same work.

**Cost.** Small, once Fix 4 lands. Put it on the Today tab, *below* the hand — it's
delight, not attention. (Wardrobe's explicit placement rule: things that ask for
action go above; things that reward go below.)

## F-5. "I've got 10 minutes"

**The idea.** The sacred interaction in wardrobe is two taps: *what do I wear
today* and *log what I wore*. Everything else negotiates for space around those.

The Home Tasks equivalent is *"I have a small window, what's the best use of it?"*
Today that requires changing the budget in Settings, which is a settings change
masquerading as a moment of intent.

**Spec.** A row on the Today tab: **10 / 20 / 30 min** chips. Tapping one deals a
one-off micro-hand against that budget without touching `budgetWeekday` /
`budgetWeekend` — highest-scoring tasks that fit, pinned and in-progress carried
along as usual (`mergeStickyHand` already does this). Tapping again or redealing
returns to the normal hand.

The dealing machinery all exists; this is a transient budget override plus three
chips. Deliberately **not** persisted — it's a moment, not a setting.

**Cost.** Small.

## F-6. Weather as a *badge*, never a filter

**The idea.** Outdoor tasks (porch, windows, gutters) already have seasonal windows
via `taskMonths`. Weather could make them opportunistic: *"Dry and 72° Saturday —
good day for the windows."*

**The hard constraint, and it's the most important sentence in this section.**
Wardrobe built a layer that *inferred* things and used them to *filter*. It was
patched four times in one day and then deleted wholesale, with a locked decision:
**a wrong guess costs more trust than hand-entry costs taps.** A related bug: a
December trip somewhere warm asked for "Winter" and filtered the sundress out
*before* scoring could see the 84° forecast.

So: weather may **add** a badge or a small nudge card. It must **never** remove a
task from the pool, change a score, or reorder the hand. Rescue-only — it widens,
never narrows. If that constraint ever feels inconvenient, that's the signal to
drop the feature, not to relax the rule.

Open-Meteo is keyless and needs no account (wardrobe uses `api.open-meteo.com` with
plain `fetch`). One call per day, cached.

**Cost.** Small–medium. **Recommendation: build it last, or not at all.** It's the
only item here that adds an external dependency to an app whose great virtue is
having none.

## F-7. Bob — an open question, not a spec

Tasks carry `owner: 'alina' | 'bob' | 'either'`, and Bob appears in the UI (an owner
badge at `:1823`, counts in Settings at `:3413`). But state is one `localStorage`
per browser, so there is no world in which Bob's completions and Alina's merge.

**So which is true?**

(a) Bob doesn't use the app, and `owner:'bob'` means "not my problem" — a filter for
her own view. Then everything is working as intended and there's nothing to build.

(b) Bob should get his list — in which case the cheapest honest version needs **no
sync at all**: a **"Send Bob his list"** button that reuses the existing
`copySprint()` clipboard plumbing to copy his due tasks as a markdown checklist,
which she texts him. Zero infrastructure, zero new failure modes, and it's how the
handoff probably already happens verbally.

**Worth noting:** wardrobe was asked directly about a second user and said a hard
NO — the app's value came from being *hers*. That may or may not apply here; a
house is genuinely shared in a way a wardrobe isn't. **This is a question for Alina,
not a decision to make in code.**

## Explicitly NOT recommended

- **Before/after photos on deep-clean tasks.** Charming, and the only idea here that
  needs real infrastructure — `localStorage` can't hold images, so it means
  IndexedDB, a byte cache, and eviction logic. Wardrobe has all of that and it was
  the single largest source of complexity in the app (plus a Supabase egress
  overage). Not worth it for a satisfaction feature.
- **Splitting `index.html` into modules.** Wardrobe split at 16k lines and it was
  right — the "one file" rule there turned out to be an accident that got written
  down as law. But the payoff arrived at 16k, and the split's real ongoing cost is
  cache-bust discipline: a version string kept in lockstep across 23 script tags,
  where missing one serves a fresh shell beside stale modules — *worse* than not
  updating at all. At 4.1k lines with zero tags to bust, Home Tasks is on the good
  side of that trade. **Revisit around 8k lines.**
- **Notifications / reminders.** Wardrobe's hard NO list, and the reasoning
  transfers: an app you choose to open is a tool; an app that interrupts you is a
  chore with a chore's emotional weight. The one exception wardrobe allowed was
  *in-app* laundry prompts — which is exactly the shape Home Tasks already uses.
- **Any AI/LLM layer.** Also on wardrobe's hard NO list. The scoring here is
  legible, debuggable, and explains itself via the "why?" modal. That's worth more
  than cleverness.

# PART 3 — Craft: making it feel finished

> *"I love the app and think it works well, but it's a bit amateur feeling. And
> some cases where too many taps to get to what I want."* — Alina, 2026-08-03

Wardrobe went through exactly this and the answer was a **presentation-only round**
(the 2026-07-21 "editorial redesign"): new palette, a display face, dark mode,
motion, focus states. **Zero schema or logic change.** It is the single highest
ratio of perceived-quality to risk available in a personal app, because nothing
that works can break.

Everything below was verified by reading the CSS on 2026-08-03. Counts are actual
counts.

## The diagnosis — "amateur" is four measurable things, not taste

1. **There is no type scale.** The stylesheet uses **12 distinct font sizes**
   (10, 11, 12, 13, 14, 15, 16, 17, 18, 20, 22, 28 px), plus 190 inline
   `style="…"` attributes carrying five more. Finished apps use five or six sizes
   total. This is the biggest single tell, and it's mechanical — nothing to do with
   taste.
2. **There is no spacing scale.** Padding values are chosen per-component:
   `14px 16px`, `12px 12px 4px 12px`, `20px 24px`, `0 12px 12px 48px`, `16px 20px`,
   `10px 24px`. Nothing lines up across components because nothing was ever asked to.
3. **190 inline `style` attributes.** Each one is a place the design system cannot
   reach, and they drift from the classes they sit beside.
4. **One typeface, one voice.** Everything is `-apple-system` at weight 500/600.
   Nothing on any screen has a different register, so nothing reads as a *title* —
   it reads as bold body text. This is why it feels like a form rather than a product.

## D-1. A type scale ⭐ highest impact per hour

Define six steps as tokens and map all twelve sizes onto them:

```css
--fs-display: 28px;  /* the one big number / hero title */
--fs-title:   20px;  /* view + card titles */
--fs-body:    15px;  /* task names, primary text */
--fs-sub:     13px;  /* secondary text, descriptions */
--fs-meta:    12px;  /* room · time · freq */
--fs-label:   11px;  /* uppercase tracked section labels */
```

Retire 10, 14, 17, 18, 22 by rounding each to the nearest step.

**⚠️ Do not fold 16px into the scale.** `.search-input`, `.filter-select`,
`.field-input`, `.field-select`, and `.zone-select` are all 16px, and that is
**load-bearing**: iOS Safari zooms the whole page when you focus an input smaller
than 16px. Whoever set those got it right. Add a comment saying so, because it
looks like an inconsistency and someone will "fix" it.

## D-2. A display face ⭐ the single biggest "feels designed" lever

Wardrobe added one line:

```css
--serif: Georgia, 'Times New Roman', serif;
```

…and applied it to headings only. That change, more than the palette, is what made
it stop looking like a form. **System fonts only** — the original design handoff
loaded a Google Font and it was rejected as an external request; the same rule
applies here, and more strongly, since this app currently has *zero* external
dependencies and that's a virtue worth protecting.

Apply to: the hero title ("Today's Hand"), `.manage-title`, `.settings-card-title`,
`.modal-title`, `.settings-stat-num` (big numbers in a serif look intentional
rather than default), and the bold line in `.empty` states.

Do **not** apply it to task names, buttons, or meta text — the contrast between a
serif title and a sans body is the entire effect; serif everywhere destroys it.

## D-3. Dark mode has two real bugs, not just polish

**Bug 1 — `--purple` and `--teal` are never defined.** Verified: zero occurrences
of `--purple:` or `--teal:` anywhere in the file. The owner badges rely on fallbacks:

```css
.owner-alina { background: var(--purple-bg, #eeedfe); color: var(--purple, #534ab7); }
.owner-bob   { background: var(--teal-bg, #e1f5ee);   color: var(--teal, #0f6e56); }
```

Those literals are light-mode colours, and since the variables don't exist, they
apply **in dark mode too** — a pale lilac chip glowing on a near-black card. Define
all four in `:root` and give them dark-mode values.

**Bug 2 — the dark block lightens the `-bg` accents but not the foreground ones.**
It overrides `--red-bg`, `--amber-bg`, `--green-bg`, `--blue-bg` and leaves `--red`,
`--amber`, `--green`, `--blue` at their light-mode values. Consequence:

`.tab.active { color: var(--green) }` renders **`#3b6d11` on `#252523` ≈ 2.4:1**.
The floor for UI components is 3:1. **And that colour is the only indicator of
which tab you are on.** The same applies to `.settings-save-btn`, `.date-save-btn`,
`.snooze-day-btn`, `.manage-hand-btn.in-hand`, `cadenceInfo`'s colour coding, and
every other accent-coloured piece of text in dark mode.

Fix: lighten all four foreground accents in the dark block (green to roughly
`#8fc45a`, and similar lifts for red/amber/blue), then check each against its
background.

**Then add `--on-accent`.** Text sitting *on* a filled accent needs its own token,
because once you lighten the accent for dark mode, white text on it fails. Wardrobe
learned this the expensive way. Current literal-white-on-accent sites:
`.mode-btn.active { color: #fff }`, `.add-btn { color: white }`,
`.header-logo-icon { color: white }`, `.modal-btn.primary { color: white }`.

> **⚠️ The gotcha that cost wardrobe a day.** Their first attempt was a
> `@media (prefers-color-scheme: dark) { .btn { color: … } }` block near the top of
> the stylesheet. It **silently lost the cascade** to a later base rule at equal
> specificity and did nothing. A custom property on `:root` is the only thing that
> works here. Do not try it as a media-query rule.

**What should stay literal white:** `.task-check-inner` and `.mc-check-inner` draw
the checkmark with `border-color: white` on a green fill. That's on the accent, not
on a surface, and it's correct. Keep it.

## D-4. Motion and feedback — this is the "joy" part

Current state: **one** `:active` rule in the entire file, **zero** `:focus-visible`,
**zero** `prefers-reduced-motion`, **zero** `tabular-nums`.

Cheap, high-return, in rough order:

- **Modals pop.** `.modal-backdrop` goes `display: none` → `display: flex` with no
  transition. This is probably the most amateur-feeling *moment* in the app because
  it happens dozens of times a day. Animate: backdrop fade + sheet slide-up on
  `cubic-bezier(.32, .72, 0, 1)`, plus a backdrop blur.
  > **⚠️ Wardrobe's rule, learned by regression:** once animated, sheets must open
  > and close **only** through `showSheet(id)` / `hideSheet(id)` helpers, where
  > `hideSheet` animates first and flips the hidden class ~240 ms later. Any code
  > that toggles the class directly gets the pop back, and it will look like the
  > animation "randomly doesn't work."
- **`:active { transform: scale(0.97) }`** on primary buttons and task cards. On
  iOS this is most of what makes a tap feel *received*.
- **`font-variant-numeric: tabular-nums` body-wide.** This app is full of numbers
  that change in place — timers, counts, minutes left, streaks. Proportional digits
  make the surrounding text jitter on every tick. One line, and it's the kind of
  thing you can't unsee once fixed.
- **`:focus-visible` rings** — currently nothing, which means keyboard and
  switch-control users get no indication at all.
- **Tab-change fade-in** and a small scale on the active tab icon.
- **`@media (prefers-reduced-motion: reduce)`** wrapping all of the above. Required,
  not optional — it's an accessibility setting, and adding motion without it is a
  regression for anyone who has it on.
- **Haptics** (`navigator.vibrate`) are a **no-op on iOS Safari** — worth knowing
  before spending time on it. The `:active` transforms carry the feedback instead.

## D-5. The completion moment deserves more than `opacity: 0.45` ⭐

Checking a task off is the reward, and it's the thing she does ten-plus times a day.
Right now the card just dims. Give it a real beat: draw the checkmark over ~200 ms,
a brief scale-up on the circle, *then* settle to the dimmed state.

This is the natural home for milestones (F-3) — the moment already exists, it's just
currently silent.

## D-6. The task card is the actual "too many taps" problem — and it isn't taps

`renderCard` (`index.html:1792`) emits **up to ten buttons per card**, all rendered
at once, all visible, all identical: `swap`, `pin`, `remove`, `snooze`,
`did earlier`, `why?`, `⏱ time it`, `started`, `🚩`, `mark due` — plus `undo` when
done. Same size, same weight, same grey, lowercase, wrapping onto two or three rows
via `.task-actions { flex-wrap: wrap }`.

So the cost isn't reaching what you want in too many taps. It's that **every card is
a control panel and you have to re-read ten identical pills to find the one you
want, every time.** That's recognition cost, and it's worse than tap cost because it
never becomes automatic.

Wardrobe hit this exactly, on its home screen: catch-up, laundry, backup, and
weather offers all competing for attention. The fix was an **attention hierarchy** —
one slot, filled in strict priority order, with everything else folded into a
single "N more things ›" line.

**Applied here:**

- **Primary stays where it is:** the check circle. Already one tap, already correct.
- **Show at most two contextual secondaries**, chosen by state rather than always:
  - not started → `started`
  - in progress → `⏱`
  - not due → `mark due`
  - done → `undo`
- **Everything else moves behind a `⋯`** opening the existing bottom-sheet modal:
  swap, pin, remove, snooze, did earlier, why?, flag. The modal already exists and
  is already styled — this is mostly deletion.
- **`did earlier` should default to yesterday.** Right now it opens a picker row and
  needs a second tap to choose; "yesterday" is the overwhelming majority case. Make
  the button log yesterday directly and put 2/3-days-ago in the `⋯` sheet.

Net effect: the card gets quieter, the common actions get *closer*, and the rare
ones stop competing. Fewer things on screen, fewer taps to what she actually wants.

## D-7. Other tap costs — asked, and mostly ruled out

I listed four candidates and asked Alina which actually bite. **She named exactly
one: the task card actions (D-6).** Recording the negatives too, so no future
session spends effort here without new evidence:

| Candidate | Verdict (2026-08-03) |
|---|---|
| **Task card actions** — ten identical buttons per card | ✅ **The one that hurts.** This is D-6, and it should be treated as the priority of the whole craft round. |
| **Budget adjustment** — Settings → card → steppers → back | Not raised as a pain. F-5 ("I've got 10 minutes") stays on the list as a *feature* she might enjoy, but **not** as a tap fix — don't justify it that way. |
| **Preset depth** — tab → category → preset → generate → load | Not a problem. Leave presets where they are; don't promote any to the Today tab. |
| **Zone selector** — native `<select>`, tap/wheel/confirm | Not a problem. Zone runs on `auto` anyway, so the control is rarely touched. Leave it. |

The useful lesson: three of the four things I could *count* weren't things she
*felt*. Counting taps finds candidates; only asking finds the answer. Ask again
before building anything else in this category.

## D-8. Desktop frame

`.app { max-width: 100% }` means on a laptop the app is a stretched mobile layout,
which reads as unfinished even though it's only ever used on a phone. Wardrobe caps
the app **and all fixed chrome** (header, tab bar) at 640px above a 700px viewport.
About nine lines of CSS.

## D-9. The rule going forward

Adopt wardrobe's, verbatim, in CLAUDE.md:

> **No hardcoded colours in new UI.** Every literal routes through a token, so both
> themes work. A `#fff` looks fine while you're building it and glows on a dark
> screen. Use `var(--on-accent)` for anything sitting on the accent — never literal
> white there.

And: **new UI uses classes, not inline styles.** The existing 190 don't need a
rewrite; they can be retired opportunistically as files are touched. What matters is
that the number stops growing.

# PART 3.5 — Review amendments (2026-08-03, after re-reading the code)

Every factual claim in Parts 1–3 was re-verified against `index.html` and held.
Six things need changing before the specs above are built as written.

**A. Fix 2 must keep type validation, not just collapse the whitelist.** The
whitelist is doing a second job the plan doesn't credit: `parsed.pinnedIds || []`
guarantees an array, `parsed.snoozed || {}` guarantees an object. A bare
`...parsed` guarantees nothing — and `applyImport` accepts **pasted JSON text**
from a Settings textarea, so this is input validation on untrusted input, on the
load path. Keep the spread, add a typed pass:

```javascript
const d = defaultState();
const merged = { ...d, ...parsed };
Object.keys(d).forEach(k => {
  if (Array.isArray(d[k]) !== Array.isArray(merged[k]) || typeof merged[k] !== typeof d[k]) merged[k] = d[k];
});
```

One place to add a field, *and* a corrupt paste can no longer take out the next
render. Self-test case 19 then round-trips garbage, not just `defaultState()`.
Also: `loadState` falls back to `STORAGE_KEY_V7` — decide deliberately whether a
v7 blob spreads through wholesale.

**B. Fix 3's harness must not share `localStorage` with the live app.** The
spec loads `index.html` into a same-origin iframe. That iframe runs `init()`,
which runs `autoBackupCheck()` → `downloadBackup()` → **writes `lastBackupDate`
to the real `hometasks_v8` key** and fires a file download; every save inside the
frame writes her actual data. Stub storage in the injected bridge before the app
script runs, or serve the harness from a second port. Also park the iframe
**off-screen** (`position:absolute; left:-10000px`), never `display:none` — a
`display:none` subtree has no layout, so every `getBoundingClientRect()` returns
0 and layout assertions silently pass on zeros.

**C. Self-test case 3 as written can never fail.** `scoreTask` *is*
`scoreTaskParts(...).total` plus jitter, so "the parts sum to the score" is an
identity. Replace it with assertions on component *values* against hand-computed
numbers for a fixed fixture. Note `parts` also carries three non-component keys
(`overdueDays`, `starvationDays`, `jitter`) excluded from `total`, so a naive
sum-all-keys case fails spuriously.

**D. Fix 4 step 3's derivable-year test is wrong.** "Earliest
`completionHistory` entry precedes the year's start" — earliest across *which*
task? A twice-yearly task retains 2024 entries while a daily task's 100-entry
history reaches back three months. Taking the minimum certifies the year as
derivable and then undercounts every frequent task in it: a wrong number
presented as an exact one. Instead stamp a `derivedSince` timestamp when the
pruning change lands and derive only for years fully after it. Don't infer
derivability from the data. (Also tell Alina the tradeoff plainly: deriving
minutes from *current* `taskTime()` means last year's total shifts when she logs
a new actual time. Correct, but a Year in Review number that isn't stable
between viewings is a surprise if unannounced.)

**E. New — Fix 4 needs a save-failure signal, shipped with it.** Raising the
history cap grows stored JSON substantially. `saveNow` catches the quota error
and `console.error`s it (`:826`) — no toast, no banner. If quota is ever hit,
every subsequent write fails invisibly and everything after that moment is lost
with no signal at all. This is a Lesson 1 item and it's *created* by Fix 4: on
save failure, set a sticky banner that doesn't clear until a save succeeds.

**F. New — the backup restore path has never been exercised.** There's a weekly
auto-download and a restore-from-file, and case 19 tests
`defaultState() → export → import`. But nobody has ever restored a real backup
file into a real browser. By Lesson 3, a restore that has never run isn't a
restore. Do one manual dress rehearsal, and make case 19 round-trip a
*populated* fixture.

**Smaller corrections.** Fix 5 misses a sixth site, `:2801` (Random Task card
uses raw `.time`). `renderCard` emits **11** action buttons, not ten. Inline
`style=` count is **202**, not 190 (already drifted — which rather makes D-9's
point). D-6 is not "mostly deletion": there are four purpose-built modals and no
generic sheet, so `.modal-backdrop` *styling* is reusable but the structure and
wiring are new. Fix 6's `<meta name="app-version">` must sit **before** the large
inline `<style>` or a 2 KB Range request won't reach it.
